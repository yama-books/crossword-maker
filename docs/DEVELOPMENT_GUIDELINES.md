# 日本語クロスワード作成機 開発指針

> Repository: [yama-books/crossword-maker](https://github.com/yama-books/crossword-maker)  
> 公開サイト: https://yama-books.github.io/crossword-maker/  
> 制定日: 2026-10-16 / 文書バージョン: 1.0  
> ステータス: 開発方針（今後の実装で更新する生きた文書）

## 1. 目的と到達点

日本語の自然な語彙から、**実際に解いて楽しいクロスワードを制作・編集・公開できるツール**を開発する。主な用途は学校教材・試験・図書館活動・個人のパズル制作。専門知識がなくても使えることを目指す。

最終的に、以下の**両方式**をサポートする。

1. **盤面先行型**：盤面サイズと黒マス配置を指定し、辞書からタテ・ヨコの単語を自動充填する。
2. **単語先行型**：使用したいテーマ語・必須語を入力し、交差と黒マスを含む盤面を組み立てる。

さらに、人間による**手動編集**と自動生成を往復できる構成にする。「自動で埋まったから完成」ではなく、自然な単語、よいカギ、解き心地の検証までを制作工程に含める。

### 開発上の優先順位

**正しい盤面 → 自然な日本語 → 編集のしやすさ → 解きやすさと面白さ → 生成速度・機能数**の順に優先する。検証できない大量生成より、少数でも品質を保証できる生成を選ぶ。

### スコープ外（当面）

- 会員登録・サーバー・課金・生徒の個人情報収集
- 大規模なAI生成APIへの恒常依存
- 多言語対応や複雑な共同編集の先行実装
- 完全自動のカギ生成だけで公開品質を保証すること

## 2. 現在地（試作品01）

2026-10-16時点のリポジトリの実装：

- `index.html`：スマホ・PC向けのプレイ画面。入力、答え合わせ、1文字ヒント、解答表示、印刷、ブラウザ内保存など。
- `puzzle.json`：6×6、ヨコ8問・タテ6問、合計14問。「学校生活と身近なことば」。
- `.github/workflows/pages.yml`：`main`からGitHub Pagesへ公開するワークフロー。
- `README.md`：使用方法と簡単なロードマップ。

**重要：今の試作品はクロスワードを解くアプリであり、盤面を自動生成するアプリではない。** 実装済みと計画中を混同しない。

**既知の技術的課題**：問題データが `puzzle.json` と `index.html` のJavaScript内に二重に存在する。更新忘れによる不整合を避けるため、後述の「単一の正本化」を早期に行う。

## 3. 日本語クロスワードの基本仕様

### 3.1 解答表記

- 解答は原則**全角カタカナ・1マス1文字**。
- 小書きの `ァィゥェォッャュョヮ` は、標準ルールでは対応する大きいカナに正規化する（例：`キップ` → `キツプ`、`シャシン` → `シヤシン`）。
- 濁音・半濁音は別の文字として扱う（`カ` と `ガ` は一致しない）。
- 長音記号 `ー` は1マスを使う。許容・禁止の個別条件はルール設定で管理する。
- ひらがな・半角カタカナ入力を受け入れ、共通の正規化関数で変換する。ただし、Unicode正規化による不要な表記変化にはテストを用意する。
- 表示上の漢字・原語表記（例：`家庭科`）と、盤面に入る読み（`カテイカ`）は別フィールドで保持する。
- 「ヂ/ジ」「ヅ/ズ」「オ/ヲ」「ヴ/ブ」などを同一視しない。読みの揺れ、分かち書き、固有名詞の扱いは語彙登録時に明示する。

### 3.2 盤面と単語枠

**標準ルール（MVPの初期設定）**

1. 盤面は長方形のマス目で、白マスと黒マスから構成する。
2. ヨコ語は左→右、タテ語は上→下に読む。
3. 白マスの連結領域は1つ（上下左右の隣接で連結）。
4. 黒マスの上下左右の連続を禁止する。斜めの接触は許可する。
5. 2マス以上連続する白マスは語枠とし、すべて正しい単語で埋める。交差位置の文字は完全一致。
6. 1文字だけの横列・縦列は独立した問題には数えない。ただし、その白マスは反対方向の有効な語枠に所属しなければならない。
7. 同一の正規化解答を同じ問題内で重複使用しない。意味が違っても同じカナになる場合は原則禁止。
8. 語の先頭に `ン` や `ー` を置かない（例外ルールがある場合は明示）。
9. 番号は上段左から行優先で、タテ・ヨコいずれかの開始マスに付ける。同じ開始マスには共通番号を付ける。
10. 黒マスの180度回転対称は**初期の推奨設定**とし、将来は切り替え可能にする。対称性は盤面成立の絶対条件ではない。

競技・出版社・教材向けの違いは、実装にハードコードせず `ruleSet` として切り替え可能にする。特別ルールは問題本文にも表示する。

### 3.3 カギ（ヒント）

- 解答語の意味が適切に導けるように書く。誤った定義や無理な語義は不可。
- 同音異義語・複数のあり得る答えがある場合、追加の文脈で絞る。
- 初級は説明中心、中級以上は言い換え・連想・語彙知識を組み合わせる。
- カギの中で答えそのものや明白な表記を不用意に提示しない。
- 学習教材では対象学年・教科・学習目標を記録し、必須語の指定を可能にする。
- AIによるヒント草案は将来許可するが、辞書的事実の照合と人間の最終確認を必須とする。

## 4. データ設計

### 4.1 単一の正本（Single Source of Truth）

問題ごとにバージョン付きJSONを1つ正本として保持する。画面、検証、印刷、解答、エクスポートはそこから生成する。

現在の `puzzle.json` とHTML内埋め込みデータの二重管理は解消する。ローカルの `file://` 起動を維持するなら、開発時JSONから埋め込み済み配布HTMLを**ビルドで生成**し、手作業で2か所を編集しない。

推奨の将来構成：

```text
/
├── index.html
├── data/
│   ├── puzzles/         # 問題の正本（JSON）
│   └── lexicon/         # 利用条件確認済みの語彙データ
├── src/
│   ├── core/            # 正規化、盤面抽出、番号付け、検証
│   ├── generator/       # 盤面先行・単語先行の各生成器
│   ├── editor/          # 編集機能
│   └── ui/              # 表示と操作
├── scripts/             # 生成・検証・ビルド
├── tests/               # 単体・回帰・統合テスト
├── docs/
│   └── DEVELOPMENT_GUIDELINES.md
└── .github/workflows/   # 検証と公開
```

この構成は**目標案**であり、現時点でこれらすべてが存在するわけではない。初期は依存関係を少なくし、JavaScript/TypeScriptベースの静的Webアプリを基本とする。

### 4.2 問題データの最低限の要素

- `schemaVersion`、`id`、`title`、`theme`、`difficulty`、`ruleSet`
- 行数・列数（正方形に限定しない）
- 白黒マスと、完成解答を表現する確定データ
- 語枠：方向、開始座標、長さ、正規化解答、漢字等の表示語、カギ、採用根拠
- 作成日時、更新日時、作成方法（手動/自動/混合）、検証状態
- カギのレビュー状態と、必要なら出典・辞書ID

盤面、語枠、番号の重複情報はなるべく導出して不整合を防ぐ。入力されるデータのスキーマ検証とマイグレーションを用意する。

### 4.3 語彙辞書

各語に `surface`（表示語）、`reading`（読み）、`normalized`（マス用表記）、品詞、語義、出典、使用可否、難易度、分野タグ、固有名詞フラグ等を持たせる。

- **辞書に存在すること**と**クロスワードに自然であること**は別に審査する。
- 固有名詞・古語・専門用語・活用形・助詞込みの表現は、規則と難易度に応じて採否を分ける。
- 機械が作った架空語や文字列を、根拠なしに登録しない。
- 辞書・データセットのライセンス、改変、再配布条件と出典を必ず確認する。外部辞書の無断コピーをしない。

## 5. 自動生成エンジン

### 5.1 共通の検証エンジンを先に作る

盤面編集、手入力、盤面先行生成、単語先行生成が、**同じ `validatePuzzle()`** を使用する。最低限のチェック：

- マス数・文字種・正規化・黒マスルール・白マスの連結
- タテ/ヨコ全語枠の抽出、開始位置と番号の再計算
- 空欄・未定義語・交差不一致・同一解答の重複
- 必須語が本当に使用されているか
- 正解データとカギの対応、全マスの解答可能性
- 盤面・カギのレビュー状態と未承認語の検出

**重大な違反は採用をブロック**し、改善可能なもの（交差の少なさ、難語の多さ、見た目の偏り）は警告とスコアで示す。

### 5.2 方式A：盤面先行生成

1. サイズ、黒マス配置、対称性、辞書・難易度を選ぶ。
2. 有効なタテ・ヨコ語枠と交差制約を抽出する。
3. 長さが合う単語候補を作り、既知の交差文字で絞る。
4. **MRV（候補数が最少の語枠から探索）**、前向きチェック、必要に応じて制約伝播（AC-3等）を実装する。
5. 矛盾時はバックトラック。探索上限・時間制限・再現用シードを設ける。
6. 成立候補を複数作り、品質スコアとレビュー状態で比較する。

### 5.3 方式B：単語先行生成

1. テーマ語・必須語・候補語、サイズと制約を受け取る。
2. 重要語を優先して、交差候補と配置位置を探索する。
3. 文字の衝突、隣接による意図しない語枠、黒マス制約、連結性を逐次検証する。
4. 必須語が入らない場合は「失敗」と理由を表示し、サイズ変更・条件緩和・別候補などを提案する。
5. 最終的に共通検証エンジンに通し、適切な語彙で未完成枠を補完する。

**両方式の統合**：編集画面上で「この語を固定」「この黒マスを固定」「残りを再生成」ができる設計を目指す。ユーザーが置いた確定マスは無断で書き換えない。

### 5.4 品質ランキング

盤面の成立を満たした候補だけを評価する。評価軸は、日常性・語義の明確さ、指定テーマ適合、交差の有効性、語長のバランス、ヒント作成の容易さ、黒マス分布、難易度の安定性、同音異義語による曖昧さ等。

重みは将来チューニング可能とし、**品質スコアが高くても機械だけでは「自然な日本語」を保証しない**。制作画面には採用理由、難語、危険なカギを示す。

## 6. 操作画面・体験設計

- はじめて使う人が「単語を入れる → 盤面ができる → 調整する → 配布する」を迷わず進められる。
- **作る画面**と**解く画面**を明確に分ける。試作品の既存プレイ機能は維持する。
- スマホは盤面のタッチ操作とカナ入力に対応し、PCはキーボードとマウスの操作性を優先する。
- 語枠選択と対応するカギを双方向に強調表示する。タテ・ヨコの方向切替を明確にする。
- 黒マス・番号・解答文字の判別に色だけを使わず、印刷時の白黒可読性を重視する。
- 手戻りに備えたUndo/Redo、保存、失敗理由表示、入力確定前のプレビューを段階的に導入する。
- 画面は余白のあるシンプルな構成とし、装飾より可読性・応答性・アクセシビリティを優先する。

### 出力仕様（段階導入）

1. ブラウザ印刷、A4問題・別紙解答、カギを含むPDF（印刷用CSSから着手）。
2. 盤面のJSON入出力、画像（PNG/SVG）。
3. Word（.docx）への編集可能な出力、複数問題の冊子化。

日本語フォントの埋め込みと印刷余白を確認し、学校の白黒複合機でも崩れないようにする。

## 8. テスト方針と受け入れ基準

### 自動テスト（最低限）

- 正常な6×6試作品を読み込み、14問の解答・開始番号・文字列が一致する。
- 正規化：ひらがな、半角カタカナ、小書きカナ、濁音、長音、許容外文字。
- 不正な語枠：長さ不一致、交差不一致、重複語、先頭の `ン`/`ー`。
- 不正な盤面：黒マス隣接、白マス分断、未入力マス、番号不一致。
- 対称配置の有無がルール設定に従って判定される。
- 同じシードと同じ辞書データで同じ生成結果に再現できる（生成機能導入後）。
- 印刷向けレイアウト、スマホ画面、キーボード操作の回帰テスト。

### 人間によるレビュー

- 各採用語の自然さ、意味、読み、学年への適合を確認する。
- すべてのカギを白紙から解き、意図しない別解がないか点検する。
- 交差で補助されずに極端に難しい語が残らないように調整する。
- A4白黒印刷でマス・番号・カギが判読できることを確認する。

### リリース基準

**重大な盤面違反0件、未完成枠0件、採用語とカギのレビュー漏れ0件、操作不能となる不具合0件。** 生成機能の追加時にも既存の「解く」機能を壊さない。

## 9. GitHub運用と作業規則

- **正本は `yama-books/crossword-maker`**。ローカルやチャット内だけで仕様・成果物を完結させない。
- 原則として1タスク1変更単位とし、コード・問題データ・テスト・関連文書を同じ変更として管理する。
- 構造変更や生成アルゴリズムなど大きな改修は作業ブランチとPull Requestを使い、検証後に`main`へ反映する。
- `main`への反映後、GitHub Actionsの成功とGitHub Pages上の実表示を別々に確認する。実行開始だけを「公開済み」と報告しない。
- 仕様の決定やルール例外はこの文書に追記し、変更理由をコミット履歴に残す。
- 機能追加前に既存ファイルと未完了作業を確認し、重複実装や既存成果の上書きを避ける。
- 公開リポジトリに秘密鍵、APIキー、学内の非公開情報、生徒の個人情報を置かない。
- 公開（Public）とライセンス許諾は別。外部データの利用条件を確認し、プロジェクト全体のLICENSEは権利方針を決めた後に設定する。
- 作業報告には「変更点、テスト結果、コミット、公開状態、既知の課題、次の作業」を簡潔に記す。
